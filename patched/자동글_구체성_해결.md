# 자동 글이 두루뭉술했던 이유와 고친 것

## 한 줄 결론

프롬프트 문제가 아니었습니다. **API 로 글을 쓸 때는 모델이 검색을 못 하고
있었습니다.** 눈을 감은 채로 쓰라고 시킨 셈입니다.

## 왜 손으로 쓰면 구체적인가

| | 손으로 (챗봇 화면) | API (지금까지) |
|---|---|---|
| 검색 | 챗봇이 **스스로 여러 번** 검색 | **안 함** |
| 페이지 읽기 | 끝까지 읽음 | 파이썬이 앞 12문단만 긁음 |
| 표 안의 숫자 | 읽음 | **못 읽음** |
| 모자라면 | 링크 타고 더 들어감 | 그대로 끝 |
| 재료 양 | 사실상 제한 없음 | 1,400자 × 3쪽 |

`은행별 금리 비교`는 거의 항상 **표** 안에 있습니다. 표를 못 읽으니
"가장 싼 은행이 어디인지"를 영영 알 수 없었습니다.

거기에 프롬프트가 `확인되지 않은 것을 단정하지 마세요` 라고 시켰습니다.
아는 게 없는데 단정하지도 말라고 하면, 모델이 규칙을 지키는 방법은
하나뿐입니다 — "은행마다 다릅니다".

**두루뭉술은 모델이 게을러서가 아니라, 모르는 것을 모른다고 말한 결과였습니다.**
정직한 대답이었습니다. 잘못은 재료를 안 준 쪽에 있습니다.

## 고친 것 네 가지

### 1. 모델에게 검색을 시킨다  (가장 큰 것)

글쓰기 전에 **검색 전담 호출**을 한 번 넣습니다. 이 호출에는 검색 도구가
붙어 있습니다. 결과를 시트에서 쓰던 **사실카드 모양**으로 받습니다.

```
[확인된 사실]
항목 | 값 | 기준일 | 출처이름 | URL
전세대출 최저금리 | 카카오뱅크 연 3.52% | 2026-09-15 | 은행연합회 소비자포털 | https://...

[확인 안 됨]
- 지점별 우대금리는 공시되지 않아 확인 못 함

[확인하는 방법]
- 은행연합회 소비자포털 > 대출금리비교 > 전세자금대출
```

`[확인 안 됨]` 칸이 핵심입니다. 모르는 것을 **모른다고 적을 자리**를 주면
지어내지 않습니다.

### 2. 표와 목록을 읽는다

| | 예전 | 지금 |
|---|---|---|
| 읽는 문단 | 앞 12개 | 60개 (본문 영역을 먼저 찾음) |
| 표 `<table>` | **못 읽음** | 읽음 |
| 목록 `<li>` | 못 읽음 | 읽음 |
| 쪽당 글자 | 1,400자 | 4,000자 |
| 쪽 수 | 3쪽 | 5쪽 |

본문을 `<article>`, `#article-body`, `.news_body` 같은 영역에서 먼저 찾습니다.
그래서 로그인·부고·관련기사 같은 메뉴가 안 섞입니다.

### 3. 분량이 재료를 따라간다

예전엔 재료가 얼마든 **무조건 7,000~9,000자**였습니다. 재료 4,000자로
8,000자를 쓰라고 하면 물을 탈 수밖에 없습니다. **두루뭉술은 산수의 결과**였습니다.

| 확인된 사실 | 분량 |
|---|---|
| 8줄 이상 | 5,000~7,000자 |
| 3~7줄 | 3,500~5,000자 |
| 3줄 미만 | **2,000~3,000자** — 늘리지 말 것 |

### 4. "쓰라" 는 규칙을 같이 넣는다

`추측하지 마세요` 만 있고 `이건 쓰세요` 가 없으면, 아무것도 안 쓰는 게
가장 안전합니다. 반대쪽 추를 달았습니다.

```
- 아래 [확인된 사실] 에 값이 5줄 있습니다. 전부 본문에 쓰세요.
- 기관·은행은 실제 이름으로. '한 시중은행' 은 실패입니다.
- 숫자는 기준일과 함께. (2026년 9월 기준 연 3.52%)
- 비교 주제면 이름 3개 이상을 표로.
```

## 켜는 법

`.env` 에 넣습니다. **첫 줄 하나면 켜집니다.** 나머지는 기본값이 있습니다.

```ini
WEB_SEARCH_ENABLED=1            # 검색 켜기 (기본 1)
WEB_SEARCH_MODEL=               # 비우면 글쓰기와 같은 모델
WEB_SEARCH_CACHE_HOURS=12       # 같은 키워드 재실행 시 아껴 씀

LENGTH_FOLLOWS_MATERIAL=1       # 분량이 재료를 따름 (기본 1)

SOURCE_NOTE_PARAGRAPHS=60       # 쪽당 읽을 문단 수
SOURCE_NOTE_CHARS=4000          # 쪽당 가져올 글자 수
SOURCE_NOTE_PAGES=5             # 읽을 쪽 수

ARTICLE_V2_CATEGORIES=*         # 질문부터 뽑고 쓰기 + 두루뭉술하면 다시 쓰기
```

마지막 줄을 권합니다. `*` 는 모든 카테고리라는 뜻입니다. 글을 쓴 뒤
모호표현 밀도를 재서, 기준을 넘으면 **한 번 다시 쓰게** 합니다.
더 나빠지면 처음 것을 씁니다.

## 되돌리는 법

전부 스위치가 있습니다. 한 줄씩 `0` 으로 바꾸면 예전 동작으로 돌아갑니다.
파일을 되돌릴 필요 없습니다.

## 시험해 보는 순서

1. 글감 **한 개**만 시트에 넣습니다.
2. `python blog_content_pipeline.py --limit 1`
3. 로그에서 이 세 줄을 봅니다.
   ```
   웹검색 재료를 모았습니다: ... · 확인된 사실 N줄 · N자
   재료 무게: 확인된 사실 N줄 / N자 → 분량 3,500~5,000자
   [v2] 갈래=source 질문=6개 확인된사실=5개
   ```
4. 나온 글에 **은행 이름과 숫자**가 있는지 봅니다.

`확인된 사실 0줄` 이 뜨면 그 주제는 검색으로 숫자를 못 찾았다는 뜻입니다.
그때는 글이 '확인하는 방법' 쪽으로 쓰입니다. 그것이 두루뭉술한 글보다 낫습니다.

## 안 되면

로그에 이 줄이 보이면 검색 도구를 못 쓴 것입니다.

```
이 모델/SDK 로는 웹검색을 못 합니다. 재료 없이 예전 방식으로 씁니다
```

`pip install -U openai` 를 해 보시고, 그래도 같으면 로그를 보내 주세요.
이 경우에도 **글 생성은 멈추지 않고** 예전 방식으로 계속 돕니다.

## 남는 한계

- 검색으로도 못 찾는 값이 있습니다. 지점별 우대금리처럼 공시가 없는 것들입니다.
  그건 `[확인 안 됨]` 으로 남고, 글에는 '확인하는 방법' 으로 들어갑니다.
- 글 한 편당 API 호출이 하나 늘어납니다. 캐시가 있어 같은 키워드를 12시간 안에
  다시 돌리면 검색은 다시 하지 않습니다.
- 제가 실제로 돌려 보지 못했습니다. API 키가 제게 없고, 회원님 도메인도
  열리지 않습니다. **코드 경로로만 확인했습니다.**
