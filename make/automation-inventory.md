# 자동화 인벤토리 (현재 운영 중인 자동화 전체 목록)

> 이 파일은 `make/automation-inventory.TEMPLATE.md` 형식에 따라 작성되었다.
> 분석 세션이 읽고 `docs/07-비교와-의사결정.md` 의 비교표를 완성한다.
>
> **⚠️ 데이터 출처에 대한 정직성 고지 (반드시 읽을 것):**
> 이 저장소(`docs/`, `src/`, `make/`)에는 각 자동화의 **존재·전략적 판정**은
> 문서화돼 있으나, **make.com 실제 모듈 구성·비용·발행빈도·각 자동화의 실제
> 상태**는 들어 있지 않다(`make/blueprints/` 폴더는 비어 있고,
> docs/05·06·07 모두 해당 값들을 "확인 필요/추정"으로 명시).
>
> **정정 이력(2026-06-13):** 저장소 문서(docs/06 §3, make/README.md)는 자동화
> #1을 "워프자동화 MAKE (광고이상건으로 중지)"로 적어, 마치 *광고 정책 사고로
> 중지된 것*처럼 다뤘다. **사용자 확인 결과 "광고이상건"은 광고 사고가 아니라
> 사용자가 작업하던 세션의 이름일 뿐이다.** 따라서 이 인벤토리는 #1을 "중지됨"
> 으로도, "광고이상건이 원인"으로도 단정하지 않는다. 관련 애드센스 원인 분석은
> 근거 없는 전제였으므로 제거했다. (저장소의 docs/06·make/README.md 에는 아직
> 같은 잘못된 표현이 남아 있어, 원하면 그쪽도 정정 가능.)
> 그래서 이 인벤토리는 **추측으로 빈칸을 채우지 않는다.** 저장소에 근거가
> 있는 값만 적고, 근거가 없는 값은 `❓ 확인 필요`로 두었다. 각 `❓` 옆에는
> **어디서 그 값을 확인할 수 있는지**를 적어, 사용자가 make.com·애드센스
> 화면을 열어 5분 안에 채울 수 있게 했다.
>
> 출처 표기: `[근거: docs/파일]` = 저장소 문서에 적힌 사실, `❓ 확인 필요` =
> 저장소에 없어 사용자 확인이 필요한 값.

## 자동화 #1

- **이름:** 워프자동화 MAKE  `[근거: docs/06 §3, make/README.md]`
  - ⚠️ 저장소 문서는 이름을 "워프자동화 MAKE (광고이상건으로 중지)"로 적었으나,
    **"광고이상건"은 광고 사고가 아니라 사용자 작업 세션의 이름**임이 확인됨.
    → 실제 자동화 이름은 "워프자동화 MAKE".
- **목적:** 워드프레스 블로그에 글(+이미지)을 make.com 시나리오로 자동 발행해
  콘텐츠 생산·발행 노동을 없애는 것. `[근거: docs/06 §3, docs/07 "make 발행 스케줄러"]`
- **플랫폼/도구:** make.com (시나리오) + 워드프레스(REST/플러그인 추정)  `[근거: docs/05 §3, docs/06 §3]`
  - ❓ 확인 필요: make 모듈 구성(HTTP? WordPress 모듈? 데이터스토어? 웹훅?)
    → **make.com 시나리오 → Export Blueprint** 로 확인 (아래 "블루프린트" 절 참고)
- **트리거:** ❓ 확인 필요 (스케줄/웹훅/수동 중 무엇인지)
  → make.com 시나리오 좌측 첫 모듈(시계 아이콘=스케줄, 웹훅 아이콘=웹훅)에서 확인
- **단계(흐름):** ❓ 확인 필요 (정확한 모듈 순서)
  → 저장소 근거상 대략 "콘텐츠 소스 → (AI 생성?) → 이미지 → 워드프레스 발행"
    구조로 추정되나 **추정이므로 확정 금지.** Blueprint로 확인.
- **사용 AI/모델:** ❓ 확인 필요 (make 안에서 어떤 AI 모듈을 썼는지 — OpenAI? Claude? 없음?)
  → Blueprint의 모듈 type 으로 확인
- **대상 블로그:** ❓ 확인 필요 (어느 워드프레스 사이트인지 — `bodybalance-labo.com` /
  `seaga.co.kr` / `sa.seaga.co.kr` 중)
  → make WordPress 모듈의 URL, 또는 Blueprint의 사이트 URL 로 확인.
  ⚠️ 만약 대상이 `sa.seaga.co.kr`/`01.sa.seaga.co.kr`(아비트라지·브리지)라면
    이는 docs/01 §C 의 "즉시 정리 대상"과 직결 — 정책 리스크 점검 대상.
- **출력물:** 워드프레스 발행 글(+이미지)  `[근거: docs/06 §3]`
- **발행 방식:** ❓ 확인 필요 (자동 공개 발행 / 초안 / 검수 유무)
  → 저장소 전략 문서는 "무검수 자동발행은 위험"이라 명시하나, **이 시나리오가
    실제로 검수 없이 공개 발행했는지**는 make WordPress 모듈의 `status`
    (publish/draft) 필드로 확인.
- **발행 빈도:** ❓ 확인 필요 (스케줄 주기 = 발행 빈도)
  → 트리거 모듈의 interval 로 확인
- **월 대략 비용:** ❓ 확인 필요 (make.com 요금제 + 안에서 쓴 AI API 비용)
  → make.com 결제 화면 + AI 콘솔 사용량으로 확인
- **현재 상태:** ❓ 확인 필요 (작동중 / 중지). **"광고이상건으로 중지"라는
  저장소 표기는 근거 없음** — 그건 자동화 상태가 아니라 사용자 세션 이름이었다.
  실제로 이 시나리오가 켜져 있는지/꺼져 있는지는 **make.com 시나리오 목록의
  ON/OFF 토글**로 확인.
- **알려진 문제:** ❓ 현재 저장소·사용자 확인상 보고된 광고 사고 없음.
  - **앞선 인벤토리의 "광고이상건 = 애드센스 정책위반/무효트래픽/게재제한 3갈래"
    분석은 철회한다.** 그 전제(광고 사고로 중지)가 사실이 아니었다.
  - 일반적 잠재 리스크(사고가 *난 게 아니라*, 무검수 자동발행을 한다면 생길 수
    있는 위험)는 docs/01 §5·docs/04 참고. 실제 발행 status가 확인되면 평가.

  현재 실제로 자동공개인지 초안까지인지는 시나리오 확인 필요.

- **월 대략 비용:** ❓ 확인 필요 (make 요금 + AI API)
- **현재 상태:** ❓ 확인 필요 (작동중/중지). 저장소엔 중지 표기 없음 → 작동중으로 보이나 미확인.
- **알려진 문제:** 무검수 자동발행 시 docs/04 품질 게이트를 우회 → Scaled Content
  Abuse 페널티 위험 `[근거: docs/01 §5, docs/06 §3 FIX 사유]`. (티스토리 비공식
  자동화 자체의 계정 위험도 별도 존재 — docs/05 §4 "주의".)

## 블루프린트(JSON) — 왜 비어 있는가 / 어떻게 채우나

요청에 "가능하면 make 시나리오 Export Blueprint(JSON)도 같이 넣어달라"고 하셨다.
**제가(이 세션이) 임의로 JSON을 만들 수는 없다** — make.com 계정에 접근 권한이
없고(`make/README.md` 방법1 참고), 모듈 구성을 모르는 상태에서 JSON을 지어내면
그건 정확히 "추측 말라"는 지시를 어기는 가짜 데이터가 된다. Blueprint는 **사용자가
make.com에서 직접 export** 해야 정확하다.

**export 절차(5분):**
1. make.com → 해당 시나리오 열기 → 우측/상단 **⋯ 더보기 → Export Blueprint**
2. 받은 `.json` 을 `make/blueprints/` 에 저장. 권장 파일명:
   - `make/blueprints/01-워프자동화-MAKE.json`  ← **최우선(상태·흐름 확정)**
   - `make/blueprints/02-티스토리-글초안.json`
   - `make/blueprints/03-티스토리-자동저장.json`
   - `make/blueprints/04-워프-이미지생성.json`
3. **커밋 전 민감정보 마스킹:** 웹훅 URL, 데이터스토어 ID, 이메일, 사이트 URL,
   토큰은 `***` 로 가린다(`make/README.md` 경고).
4. 넣은 뒤 "blueprint 확인해줘"라고 하면, 위 `❓ 확인 필요` 칸들을 **실제
   모듈 구성대로** 채워 이 인벤토리를 확정한다.

  - 후보: #1 워프자동화 MAKE, #2 티스토리 글 초안 — 둘 다 **실제 발행 status가
